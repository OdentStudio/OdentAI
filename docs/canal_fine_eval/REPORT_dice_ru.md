# Dice по размеченным данным: мелкая сетка против нынешнего второго прохода

2026-10-07, Linux (RTX 4090), ветка `canal-enhance`. Отвечает на пункт 6
рекомендаций `REPORT_ru.md` и на шаги 2–4 `HANDOFF_LINUX_canal.md`.

Данные: `nnUNet_raw/Dataset003_Dental9` — **70 отложенных кейсов** с ручной
разметкой (20 DentVoxel, 50 ToothFairy3). Веса `models/dental9.onnx`
(sha256 из `SHA256.txt`, совпал), окружение `.venv-linux`,
onnxruntime-gpu 1.23.2 — 1.24.4 нет колёс под Python 3.10; на 1.23.2 собрана
нынешняя Linux-сборка.

## Главное в двух строчках

1. **Триггер «канал сломан» не сработал ни на одном из 70 кейсов.** Поэтому
   `B (fine по триггеру)` совпал с `A (продакшен)` **побайтово** на всех 70 —
   размеченный набор не может ни подтвердить, ни опровергнуть пользу мелкой сетки.
2. **Размеченный набор лежит на шаге 0.3 мм, а клиника присылает 0.08–0.25 мм.**
   Набор не представителен ровно в том измерении, на котором работает мелкая
   сетка: на нём 0.25 мм — чистая интерполяция, новой информации нет.

## Как это читать

- **Конвейер цел.** На 20 кейсах DentVoxel (та самая выборка из README)
  средний Dice **0.9697** против 0.9619, записанных в README в сентябре.
  Не хуже; разница в большую сторону — от тайла 160×320×320, который берётся
  на карте с 24 ГБ вместо 128×256×256. `scripts/test_inputs.py` — 13 из 13,
  `py_compile` чистый.
- **Принудительные конфиги вредят оба.** `D (match)` −0.0039,
  `C (fine)` −0.0075 по каналу. Это подтверждает по разметке то, что
  Windows-сессия видела по объёмам: ни один из проходов нельзя включать всем
  подряд, оба остаются по триггеру. Прежний вывод «принудительный второй проход
  вреден» (README) остаётся в силе и теперь измерен на 70 кейсах.
- **Вред сосредоточен на слэбах ToothFairy3** (−0.0101 у fine), а на
  полноразмерных сканах DentVoxel он почти нулевой (−0.0011). Клиника
  присылает полные головы, а не слэбы.
- **Проверенная и отклонённая гипотеза.** Напрашивалось условие: запускать
  мелкую сетку, только если исходный скан тоньше рабочей сетки 0.3 мм. Чтение
  заголовков 22 клинических сканов (`/media/ilya/32EE384DEE380B9B/Dental`)
  показало, что **все они 0.08–0.25 мм**, включая Zyga (0.2 мм), где мелкая
  сетка как раз разломила здоровый канал на 2 куска. Значит такое условие
  клинические случаи не разделяет и проблему Zyga не решает. Пользу оно всё
  же приносит в одном: защищает от скана, уже лежащего на 0.3 мм (наши
  обучающие NIfTI, переэкспорт) — на таких мелкая сетка только теряет, что
  и показали эти 70 кейсов.

## Что это значит для решения

Критерий приёмки из handoff («B ≥ A по среднему Dice канала, ни одного кейса
хуже чем на 0.02») формально выполнен — B равен A в точности. Но выполнен
вхолостую: на этих данных второй проход не запускается вообще. Значит
размеченный набор говорит только одно, зато твёрдо: **добавление режима `fine`
по триггеру ничем не рискует на отложенном тесте.** Доказательство пользы
по-прежнему одно — Колкова (0.15 мм, 105 → 305 мм³, полный ход), и оно не на
размеченных данных.

Чтобы получить Dice на том, ради чего проход делается, нужна ручная разметка
канала хотя бы на 3–5 клинических сканах 0.1–0.2 мм, где первый проход рвёт
канал. Иначе решение остаётся инженерным, а не измеренным.
